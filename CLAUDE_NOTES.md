# Project Notes

- `skills/writing-skills/render-graphs.js` currently fails under the root `"type": "module"` package setting because it uses CommonJS `require`. Graphviz `dot` itself **is** installed (verified 2026-08-26), so a DOT block can be verified without that script: extract the fenced block and pipe it through `dot -Tsvg -o /dev/null`.
- For Git-installed Codex marketplaces where the plugin lives at the repository root, use a marketplace plugin source of `"source": "url"` with the repository URL and ref. A repo-cloned marketplace entry using `"source": "local", "path": "./"` can be registered by `codex plugin marketplace add` but then skipped in `/plugins`.
- Skills that resolve a trunk/base branch must **detect** it, never assume `main`. This user deliberately configures git to use `master` as the default branch for new repos. Detect with `git rev-parse --verify --quiet master` / `main` (use whichever exists; ask if both or neither), not by hardcoding `main` or trying it first. Applied in `external-code-review` (Step 2) and `finishing-a-development-branch` (Step 2) in v1.4.0.
- Skill-triggering tests (`tests/skill-triggering/run-test.sh`) shell out to a real `claude -p --plugin-dir <repo-root>`, which loads skills from the **working tree** — no plugin reload needed to test an in-progress skill. Each run can take minutes (300s timeout). The description frontmatter is what drives triggering, so editing a skill's *body* after a GREEN pass does not require re-running the trigger test.
- Skill prose should describe platform capabilities, not exact tool names, when the same concept exists across agent harnesses. Exact names such as `TodoWrite`, `update_plan`, `write_todos`, or `todowrite` belong in mapping/bootstrap docs as known examples; the core skill should tell the agent to discover the available runtime tool and fall back gracefully.
- Treat user-supplied reference docs for a task as session input, not repo documentation, unless the user explicitly asks to keep them. External CLI docs can stale quickly; implement against them, but do not commit local copies or README links to those copies by default.
- **Comparing against upstream Superpowers:** the fork point is upstream tag `v5.0.6` (commit `eafe962`, 2026-03-25) — it exists as a tag in the upstream repo, so `git diff v5.0.6..HEAD -- <path>` there separates upstream improvements from this fork's deliberate changes. Constraints any port must respect: branches not worktrees, controller-commits-only (via `commit-message` skill), resume-same-implementer for review fixes (upstream independently adopted the same rule in v6.0.0 — the divergence is validated, not a drift to fix), and the fork's own skills (external-review, using-stitch, …). - **Independent review under Codex:** never invoke Codex as the external reviewer when the controller is Codex; use a different model family such as `claude -p`. A non-zero/empty-looking capture is not sufficient evidence of a failed review: preserve and inspect the reported output file, log, and session/transcript before retrying. Limit a document-review request to one session unless that evidence proves it produced no review.
- **Current Claude headless result shape:** with Claude Code 2.1.235, `claude -p --output-format json` can produce a transcript-style JSON array rather than one result object. The successful review run on 2026-08-19 ended with an item whose `type` was `result`; consumers must preserve native JSON and locate the terminal result rather than assuming top-level `.result`. That run also directly verified `--safe-mode`, `--permission-mode dontAsk`, and a preassigned `--session-id`.
- **Measure reviewer runtime at the process:** shell-tool wall time can include minutes spent waiting for user approval before the reviewer starts. Timeout and status reporting must use independently measured process elapsed time or explicitly labelled provider runtime, not the duration reported for the surrounding tool call.
- **Historical removed-adapter lesson - Review-attempt locks must examine the whole chain:** once `--after-terminal` creates more than one directory for a stable review key, returning the first glob match can hide a newer live attempt and permit a duplicate. Find every exact-key match, reject any live match, and validate retries against the unique chain tail.
- **Historical removed-adapter lesson - Reviewer lifecycle paths and identities must be self-canonicalizing:** canonicalize the temp root before constructing or printing run paths, and have each detached supervisor record its own PID/start identity. Parent `$!` values and non-canonical `$TMPDIR` paths are not reliable across `setsid`, macOS `/var` symlinks, or later tool calls.
- **PowerShell `Start-Process -ArgumentList` does not quote path elements:** explicitly embed quotes around script and run-directory arguments, then test both the checkout and temp path with spaces under Windows PowerShell 5.1.
- **PowerShell `Start-Process` resolves bare `NUL` as a relative path:** detached Windows standard input must use the absolute `\\.\NUL` pseudo-stream. This is unrelated to the repository's storage device and still requires native Windows verification because Linux PowerShell does not implement the same launch/device behavior.
- **Historical removed-adapter lesson - The native adapter targets Windows PowerShell 5.1 only:** it is included with supported Windows client systems and avoids requiring Git Bash or a separate PowerShell 7 installation. Reject PowerShell 7 before dispatch; Linux can test only that negative gate, while lifecycle verification remains a native Windows checkpoint.
- **Historical removed-adapter lesson - Stable-key recovery is a conditional create, not a lookup-only operation:** if managed-review start output or `RUN_DIR` is lost, reissue ordinary `start` only with the exact original profile, stable key, canonical work directory, and prompt/scope semantics. A prompt profile needs the retained prompt file or a recreation with the exact original bytes, and profile preflight must still pass before the adapters inspect the registry. If any semantic input is uncertain, fail closed rather than risk launching a different review.
- **Historical removed-adapter lesson - Separate live-provider evidence from deterministic adapter evidence:** a Claude-backed trigger test that times out without model output and a managed review blocked before launch prove neither success nor an implementation defect. Record these as unverified environmental gates while reporting deterministic suite results independently.
- **Codex-hosted Claude reviews use direct foreground execution (2026-09-26):** Linux Codex CLI 0.157.1 / Claude Code 2.1.283 verified foreground PTY polling through 900 seconds, real document/code reviews and cancellation. The earlier persistent approved shell requirement is superseded; use `skills/external-review/invoking-reviewers.md`. macOS/WSL remain unverified and native Windows unavailable. Direction A is unchanged.
- **Do not use `claude -p` as a proxy for an interactive Claude Code controller:** headless mode may change controller behavior. Automated behavioral and live tests for universal review should exercise the actual Codex-controller-to-`claude-prompt` direction; validate the established Claude-controller-to-`codex-review` direction in a normal interactive plugin session, while retaining its static mapping and deterministic adapter coverage.
- **`external-code-review/SKILL.md` prose is test-pinned:** `tests/codex-plugin/validate-codex-plugin.py` asserts on exact substrings inside that skill — both reviewer-selection table rows, the phrase "sibling `external-review` skill's absolute source directory", and the sentence `Stop with "nothing to review" for empty or invalid scope.` An editorial rewrite that rephrases any of them fails the validator. Run `python3 tests/codex-plugin/validate-codex-plugin.py` before and after editing it. The pinning is deliberate — those strings decide which model reviews what, so drift should fail loudly rather than pass silently.
- **Write skills for a stateless tool caller, not for a shell session:** an agent's every shell call is a fresh process, so a skill that shows `"$ADAPTER" start …` and then `"$ADAPTER" wait "$RUN_DIR"` is unusable — the variable is empty by the next call. Any value that must cross a step boundary has to be recorded as a literal in the agent's own reply. This was lost once already: the pre-managed `external-review` skill carried the warning, the managed rewrite dropped it, and both the user and an external Codex reviewer then failed to parse the result. Related failure mode in the same rewrite: replacing numbered imperative steps with declarative policy prose. A sentence like "preflight runs before key lookup" is true and tells an executing agent nothing to do. Before deleting operational prose during a compression pass, ask whether the *code* now enforces it — if it does not, the prose is the mechanism (this is how the trunk-detection rule above got dropped and had to be restored).
- **Never assume another harness lacks a capability — check `skills/using-superartes/references/codex-tools.md` first.** It is the authority on Codex equivalents (`Task`→`spawn_agent`/`wait`/`close_agent` behind `[features] multi_agent = true`, task lists→`update_plan`, named agents→a `worker` spawned with the agent prompt file's content); `docs/README.codex.md` carries the user-facing setup. Assuming "subagent is a Claude Code concept" led to designing a needlessly split same-model fallback, when the existing mapping already made the two reviewer-prompt templates work unchanged on both sides. Assuming a capability is *absent* is the expensive direction of this error: it invents machinery to replace something that already exists. The same instinct also misjudged the local toolchain twice in one session — `dot` and `pwsh` were both installed. Check, do not infer.
- **Sabotage-test a suite by breaking its target, not its tests — the survivors are the finding.** Point the suite at a runner that does not exist and count what still passes. Both external-review runner suites reported green while testing nothing: the POSIX one left 3 passing, the PowerShell one 14, because `pwsh -File <missing>` exits **64** — the same code the runner uses for every usage error — while `bash <missing>` exits 127, which collided with only one expected code. The fix is a guard at the top of the suite (`if [ ! -f "$RUNNER" ]; then … exit 1`), which is worth more than tightening individual assertions: an exit-code assertion only means something if the harness failing cannot produce that same code. Reading the suite would never have shown this.
- **Four ways a test can report success without testing anything, all seen in one session.** A helper that calls `pass`/`fail` inside `$( )` loses the counter increment to the forked subshell, so the suite prints `0 failed` while failing. An unvalidated empty path makes `[ -d "" ]` checks pass for a run that never started. In PowerShell, `Get-Content -Raw` on an empty file returns `AutomationNull`, and `[string]`-casting it stays null, so `.Trim()` throws *before* the assertion counts itself — three assertions vanished silently and the total simply read lower. And an assertion that hand-writes the file it then checks tests only its own `printf`. Assert emptiness with `"$(...)"` interpolation, never a `[string]` cast; make helpers signal through exit status and a global, never through `$( )`.
- **Detaching a background process: the failure is always in what still holds a handle.** `nohup setsid cmd >/dev/null 2>&1 &` works, but `setsid` ships in util-linux and is **absent on stock macOS** — guard it and fall back to a `set -m` subshell. Redirect the launcher's own stderr to a file, never `/dev/null`, or "the reviewer never started" becomes a permanent silent wait. In PowerShell, `Start-Process` without redirecting the child's three streams leaves it holding the caller's stdout handle, so `-Wait` blocks for the whole job; and `Start-Process -RedirectStandardOutput/Error` pumps those streams **through the parent**, so a parent that exits by design can never fill them — a detached worker must write its own diagnostics file. On Windows `-Wait` waits on a job object, i.e. the whole process tree, which no redirect opts out of.
- **When a check produces a false positive, remove the collision rather than teaching the check to tolerate it.** The plugin validator scans the runners for a bare `-m` so this repository can never pin the user's model. Broadening it to a whole-file scan collided with the shell builtin `set -m`; a `(?<!set )` lookbehind fixed that and quietly opened a hole, because *any* token ending in `set` disarms it (`codex exec $preset -m gpt-5` slipped through). `set -o monitor` is the identical builtin under a name that does not collide, so the strict pattern needs no exception at all. Every tolerance added to a guard is a hole shaped like something you did not think of.
- **A measurement outlives the text it measured.** Two claims in the same plan went stale the same way: a "150 words" budget counted on a draft that was then revised to 191, and code blocks that were accurate until review rounds changed the code. Neither fails loudly. Re-measure at the point of use, and when a plan asserts a number, give it a step that recomputes it rather than trusting the prose.
- **For a skills library, review the prose by executing it, not by reading it.** Skills are the product; an agent runs them. Eleven defects in one task's SKILL.md rewrite survived a faithful spec review and were only found when a reviewer ran the documented commands against a stubbed CLI: a `status` subcommand the Completion section depended on but the command block never introduced, undeclared `$PLACEHOLDER` notation mixed with literals-to-paste-back, a recovery recipe returning marker-file paths where a directory was expected, and a completion flowchart with **no exit for a failed launch** — an agent would wait forever, because the red "never start a second review" octagon blocked the only reasoning path out. Ask a reviewer to *perform* the skill and report where it stopped making sense.
